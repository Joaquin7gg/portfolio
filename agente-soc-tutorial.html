Construye tú mismo un agente de triaje SOC local

Cómo reproducir el proyecto desde cero, paso a paso, con el razonamiento detrás de cada decisión. No es solo "escribe esto": es por qué se escribe así, que es lo que de verdad se aprende.

Nivel: intermedio (Python + terminal) Tiempo: un fin de semana largo No necesitas: saber de IA ni de ciberseguridad

Lo que vas a montar: un agente de IA local y offline que lee logs de seguridad, detecta patrones de ataque con código determinista, los mapea a MITRE ATT&CK y deja que un modelo pequeño redacte el informe. Con un harness que mide si el modelo es fiable.

La regla que decide todo

Antes de escribir una línea, interioriza esto, porque condiciona el resto:

El código detecta. La IA narra.

Toda la detección (contar, cruzar, comparar, ordenar) la hace Python determinista — código que siempre da el mismo resultado con los mismos datos. El modelo de lenguaje solo redacta el informe a partir de hallazgos que el código ya encontró. Nunca detecta, nunca cuenta, nunca decide.

¿Por qué? Porque un modelo pequeño (3-4B parámetros, lo que cabe en 4 GB de VRAM) alucina: se inventa datos con seguridad. Si le dejas contar ataques, un día "verá" una IP que no existe. Manteniéndolo lejos de la detección, ese riesgo desaparece por diseño, no por suerte. Este reparto también imita a los productos SOC reales: no es un apaño por tener poca máquina, es la arquitectura correcta.

Guárdate esta regla

Cada vez que dudes "¿esto lo hace el código o la IA?", la respuesta es: si implica contar o comparar, el código.

Fase 0El entorno

0.1 · Python de verdad

En Windows, cuidado: puede que tengas unos "Python" falsos que son atajos a la Microsoft Store (versión 0.0.0.0). Comprueba:

python --version

Si no sale un 3.11 o 3.12 real, instálalo desde python.org marcando "Add Python to PATH", o con winget install Python.Python.3.12.

0.2 · El motor de IA local: LM Studio

Descarga LM Studio. Es el programa que ejecuta modelos de IA dentro de tu ordenador, sin internet — la clave de la privacidad del proyecto.

0.3 · Elegir el modelo (la primera lección)

En LM Studio, busca y descarga Llama 3.2 3B Instruct, cuantización Q4_K_M (~2 GB). La decisión importante es cuál eliges, y por qué no uno más grande:

  • Tu modelo tiene que caber en la VRAM. Con 4 GB, un modelo de 6 GB no entra: se reparte con la RAM del sistema y va lentísimo.
  • LM Studio te avisa con una etiqueta verde "Full GPU Offload Possible" cuando cabe entero. Fíate de esa etiqueta, no del número de parámetros: hay modelos "4B" cuyo fichero pesa 6 GB.
  • La cuantización (Q4) es lo que hace que quepa: encoge el modelo a costa de una pérdida de calidad mínima. Para redactar un informe, esa pérdida no importa.

Arranca el servidor: pestaña </> (Developer) → Start Server. Queda escuchando en http://localhost:1234 con una API compatible con la de OpenAI.

0.4 · El proyecto Python

mkdir soc-triage-agent && cd soc-triage-agent
python -m venv .venv
.\.venv\Scripts\Activate.ps1

Dependencias mínimas (requirements.txt): solo requests y python-dotenv. Nada de librerías pesadas de IA — el modelo vive en LM Studio, tú solo le hablas por HTTP. Verifica que puedes hablar con el modelo:

curl http://localhost:1234/v1/models
⚠ Tropiezo · el nombre del modelo

Apúntate el id que devuelve (p. ej. llama-3.2-3b-instruct): tiene que ser el nombre exacto. Usar un genérico como local-model parece funcionar pero falla en cuanto el modelo se descarga por inactividad. Con el nombre real, LM Studio lo carga solo cuando llega la petición.

Fase 1El primer detector y el informe

Empieza con un solo formato: el log de SSH (auth.log de Linux), que apunta cada intento de conexión remota.

1.1 · El parser (código, determinista)

Una función que lea el fichero y convierta cada línea en un diccionario. Una expresión regular basta. Solo te interesan cuatro cosas: hora, usuario, IP, y si fue Accepted o Failed.

# la forma, no el código completo (ver src/tools.py)
def parse_auth_log(ruta):
    eventos = []
    for linea in open(ruta, encoding="utf-8"):
        m = PATRON.search(linea)
        if m:
            eventos.append({"hora": ..., "usuario": ..., "ip": ..., "estado": ...})
    return eventos

1.2 · Los detectores (código, determinista)

Cada detector recibe los eventos y devuelve una lista de "hallazgos". Escribe tres, cada uno buscando un patrón:

DetectorQué buscaSeveridad
fuerza_brutaUna IP con muchos fallos (≥5)media
posible_compromisoMuchos fallos y luego un acierto desde la misma IPalta
horario_inusualUn acceso correcto de madrugadabaja

El del compromiso es el interesante: recorre los eventos en orden, cuenta fallos por IP, y si aparece un Accepted desde una IP que ya acumulaba fallos, es sospechoso. Esto es contar y cruzar — trabajo del código. Un hallazgo es un dict simple: {tipo, severidad, ip, detalle}.

1.3 · El mapeo a MITRE (código, una tabla fija)

MITRE ATT&CK es un catálogo estándar donde cada técnica de ataque tiene un código. Haz un diccionario que traduzca tu tipo de hallazgo a su técnica:

MAPA = {
    "fuerza_bruta": {"tecnica": "T1110", "nombre": "Brute Force", ...},
    ...
}

Tabla fija en código, no generada por la IA — así el modelo no puede inventarse códigos que no existen.

1.4 · El informe (aquí, y solo aquí, entra la IA)

Manda los hallazgos ya detectados al modelo con un SYSTEM_PROMPT que le diga: "eres un analista, NO detectes nada nuevo, solo redacta y explica estos hallazgos". Recibe el texto y guárdalo.

Detalle crítico (lo aprenderás midiendo en la Fase 2)

Ordena los hallazgos por severidad en Python antes de mandarlos, y dile al modelo "ya vienen ordenados, respeta el orden". No le pidas que ordene él.

1.5 · El orquestador y la auditoría

Un agent.py que llama a todo en orden fijo: parsear → detectar → enriquecer → informe. Y en cada paso, escribe una línea en audit.jsonl (JSON Lines): qué herramienta, cuándo, con qué resultado. Esa traza es lo que demuestra "mentalidad de seguridad": la herramienta deja rastro. Verifica con un modo --sin-ia que salte el modelo y solo enseñe la detección — debe funcionar sin LM Studio siquiera.

Fase 2El harness: medir en vez de suponer

Esta es la fase que diferencia el proyecto de un juguete. Un modelo de IA no da siempre la misma respuesta. Mirar una ejecución no te dice si es fiable, igual que tirar una moneda una vez no te dice si está trucada. Necesitas medir.

2.1 · La regla del harness

Escribe un eval.py que ejecute el informe N veces (20 está bien) y cuente los aciertos con comprobaciones de Python deterministas. Nunca uses otra IA para juzgar: un juez que también alucina no te dice nada.

2.2 · Qué se comprueba

La "verdad de referencia" sale de los propios hallazgos (deterministas, idénticos en las N ejecuciones — lo único que varía es el modelo). Con eso, comprueba en cada informe:

  • ¿Menciona todas las IPs detectadas? (no se deja hallazgos)
  • ¿Aparece alguna IP que NO venía de los hallazgos? (la comprobación estrella: detecta alucinaciones)
  • ¿Aparece algún código MITRE inventado?
  • ¿Tiene las tres secciones? ¿Ordena por severidad? ¿Etiqueta la gravedad?

2.3 · La lección que caza el harness

⚠ El bug que solo se ve midiendo

El informe ordenaba mal por severidad 1 de cada 3 veces, enterrando lo grave debajo de lo leve. ¿La causa? Le estábamos pidiendo a la IA que ordenara. Y ordenar es comparar, o sea trabajo del código. Movimos el sorted() a Python y pasó a acertar el 100%. Sin el harness, ese fallo habría estado ahí para siempre, invisible.

Ese es el argumento de por qué el harness existe: no para sacar un número bonito, sino para enterarte cuando te equivocas.

Truco de método

Cuando cambies una comprobación (no el modelo), no gastes GPU reejecutando. Guarda los informes de una tanda y "repúntualos" con las comprobaciones nuevas. Aísla el efecto de tu cambio y es instantáneo.

Fase 3Un segundo formato de log

Aquí demuestras que tu arquitectura aguanta. Añade el Firewall de Windows (pfirewall.log), que no habla de contraseñas sino de conexiones permitidas (ALLOW) y bloqueadas (DROP).

3.1 · Detección de formato por contenido

El agente debe distinguir qué log le has dado mirando el contenido, no el nombre del fichero (un fichero renombrado sigue siendo lo que es). El firewall de Windows escribe una cabecera #Software: Microsoft Windows Firewall que lo identifica sin ambigüedad.

3.2 · Parser, detectores y tabla propios

Un firewall ve cosas distintas, así que le tocan detectores distintos — sobre todo reconocimiento (alguien mirando qué hay antes de atacar):

DetectorPatrónMITRE
escaneo_puertosBloqueos contra muchos puertos de una máquinaT1046
barrido_redBloqueos contra muchas máquinasT1018
acceso_tras_bloqueosMuchos DROP y luego un ALLOWT1110+T1021

Tabla MITRE aparte de la de SSH: mezclarlas acabaría con un hallazgo de firewall etiquetado con una técnica de contraseñas.

3.3 · La prueba de fuego

Diseña un log sintético donde cada detector tenga su escenario sin pisar a los demás (el escáner ataca una máquina, el barrido usa un puerto). Y mide.

Resultado esperado si lo has hecho bien

20/20, sin tocar una línea del código de IA. Esa es la prueba de que la regla de oro funciona: añadir un formato es escribir parser y detectores; la IA ni se entera. Si te ves tocando el prompt para añadir un formato, algo va mal.

Importante: mete el log nuevo en la suite del harness desde el primer día. No lo construyas y midas después — así descubres los problemas antes de tomar decisiones sobre ellos.

Fase 4El detector que correlaciona

Este detector es el que mejor demuestra por qué la detección es del código. Una shell inversa: cuando el atacante entra, no es él quien sigue llamando — es tu máquina infectada la que le llama a él (así esquiva al firewall, que vigila lo que entra, no lo que sale).

4.1 · Por qué es distinto a los demás

Los otros detectores cuentan una cosa. Este correlaciona dos hechos separados en el tiempo:

  • Una conexión saliente hacia un puerto raro (fuera de una lista blanca: web, DNS...).
  • Que el destino sea una IP que ya te estaba atacando antes en el mismo log.

Por separado, cada hecho es tibio. Juntos, confirman la cadena completa: reconocimiento → acceso → control.

4.2 · El código es trivial; ese es el punto

ips_hostiles = {e["ip"] for e in eventos if e["accion"] == "DROP"}
# ... más adelante, por cada salida rara:
confirmado = destino in ips_hostiles   # <- la correlación, en una línea

Un set y una comprobación de pertenencia. Exacto, e igual de rápido con 60 eventos que con 60.000. Ahora imagina pedirle eso a un modelo de 3B: "recuerda todas las IPs bloqueadas de las primeras 40 líneas y compáralas con el destino de la 50". Es lo que peor hace. Y no fallaría siempre — fallaría a veces.

La conclusión que va en tu portfolio

El reparto código/IA no es una excusa por tener poca VRAM. Con un modelo diez veces mayor, esto seguiría siendo trabajo de un set. La correlación es del código, punto.

Haz que el detector distinga dos casos: destino con antecedentes → alta; destino desconocido → media (puede ser una VPN legítima; avisa, no acuses).

Fase 5El experimento honesto

Llega la pregunta obvia: "un agente de verdad elige sus propias herramientas, ¿por qué el tuyo va en pasos fijos?". La respuesta fácil es "porque el modo autónomo va mal con modelos pequeños". Pero eso hay que medirlo, no afirmarlo.

5.1 · Construye el modo autónomo de verdad

Usa el tool calling de la API (le pasas las herramientas al modelo y él decide cuál llamar). Y pónselo fácil a propósito, para que el experimento sea justo: herramientas sin argumentos, el prompt le dice qué orden tiene sentido, y dale reintentos por turno. Si aun con las cosas fáciles falla, la conclusión es más fuerte.

5.2 · Mídelo con el mismo harness

 OrquestadoAutónomo
Informes perfectos18/200/10
Llegó a escribir informe20/202/10
No se repitiópor diseño0/10
Respetó el orden básicopor diseño10/10

Cero de diez. Se atascaba llamando a la misma herramienta once veces, sin leer que la respuesta no cambiaba. Pero respetó el orden 10/10: entiende la dependencia, no actúa al azar. No es que no sepa qué hacer — es que no sostiene el protocolo.

5.3 · El límite honesto (esto es lo que te distingue)

Afirma solo lo que mediste

Ese fallo lo emite en parte el motor de LM Studio, no solo el modelo. La conclusión honesta es: "con esta pila concreta (Llama 3.2 3B + LM Studio 0.4.19), el orquestado gana 18/20 a 0/10". No "los modelos pequeños no valen para agentes" — eso sería afirmar más de lo que mediste. Convertir una opinión en un resultado con números y sus límites claros: eso separa un proyecto de estudiante de uno serio.

Fase 6Medir tu propio hardware

No supongas que "va bien". Mídelo mientras trabaja. Con nvidia-smi en un hilo aparte, captura durante una inferencia real:

  • Velocidad (tokens/s). En una RTX 3050 salieron ~52-56.
  • Uso de GPU. Si está al 85%, el modelo está entero en la gráfica. Si está ocioso (~20%) y va lento, se reparte con la RAM: elegiste mal el modelo.
  • VRAM. Aquí, 80% de los 4 GB. De eso, solo la mitad es el modelo; el resto es la ventana de contexto.

El techo real, y cómo predecirlo

Mide cuántos tokens cuesta el prompt por hallazgo (aquí, ~115-140). Con una ventana de 8.192 tokens, sale un techo de ~50 hallazgos por informe. Eso convierte "probar un log gigante" en una predicción falsable: no dará informes peores, dará un prompt que no cabe. La detección seguirá perfecta (es Python). Y la solución no será un modelo mejor, sino paginar los hallazgos — otra vez, código.

⚠ Ojo con extrapolar de una sola medición

Mide tres logs distintos, no uno. En este proyecto, la recta "tokens por hallazgo" parecía perfecta con un punto y fallaba un 12% con tres: los detectores que escriben detalles largos cuestan más. Un punto miente.

Fase 7Publicarlo bien

7.1 · Git desde el principio

No dejes dos días de trabajo en una carpeta sin red. git init, y commitea cada pieza con un mensaje que explique el porqué, no solo el qué.

7.2 · Qué NO subir

Un .gitignore que excluya: el .env, el entorno virtual .venv, los informes generados, los resultados del harness y los ajustes locales del editor. Solo datos sintéticos en el repo: IPs de rangos de documentación (RFC 5737: 192.0.2.x, 198.51.100.x, 203.0.113.x), nunca reales.

7.3 · Privacidad al publicar

Antes de hacerlo público, barre el historial entero (no solo el estado actual) buscando: tu correo personal, secretos, claves, IPs reales. Lo que entra en un repo público puede quedar cacheado aunque lo borres. Usa el correo @users.noreply.github.com de GitHub en los commits:

git config --local user.email "TU_ID+usuario@users.noreply.github.com"

7.4 · Licencia

Sin licencia, tu código está protegido por defecto: público solo significa visible, no usable. Añade un fichero LICENSE con la MIT (la más permisiva) para que otros puedan usarlo manteniendo tu crédito.

La meta-lección

Si te llevas una sola cosa de construir esto, que sea esta:

Desconfía del resultado que te da la razón demasiado fácil, y mídelo dos veces.

En este proyecto, cuatro veces se dio algo por bueno sin comprobarlo, y las cuatro estaba mal:

  • El código que ordenaba mal 1 de cada 3 veces, invisible hasta medir.
  • Una config que "funcionaba"... solo porque el modelo estaba cargado a mano.
  • La afirmación sobre el modo autónomo, escrita con seguridad y sin un número detrás.
  • Una predicción de rendimiento a punto de escribirse con una sola medición.

Las cuatro cayeron por lo mismo: mirar dos veces en vez de suponer. El agente que construyes es la excusa; ese reflejo es lo que de verdad aprendes, y en un perfil de seguridad vale más que cualquier detector.
